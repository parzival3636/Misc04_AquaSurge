Elevation: query Open-Elevation API (free, no key) per settlement coordinate — real values, not estimated.
Distance to river: compute real geodesic distance from each settlement's coordinates to the nearest river polyline (can trace the
river manually from OSM and compute point-to-line distance with shapely).
Historical ﬂood ﬂag: binary ﬂag per settlement — set to 1 only if you ﬁnd real evidence (news reports, district disaster
management records) that the settlement has ﬂooded before; otherwise 0. Document your source per settlement in a
comment/footnote so this isn't fabricated.
2.2 Timestep construction (real event, replayed honestly)
Take your real rainfall time series for the chosen historical event and bucket it into 8 timesteps (T1 = early/light rain building to T8 =
peak). Each settlement's rainfall_mm[Ti] should be the real recorded value for that time window at the nearest rain-gauge/grid-cell to
that settlement — not the same number applied to every settlement.

4. Member C — Viewer, Interactivity & Evidence Presentation
4.1 Map rendering (Leaﬂet)
Settlement markers colored by risk_level[current_timestep] — real per-point recoloring driven by state.json, not a ﬁxed
palette assigned once.
Road lines colored by status[current_timestep] — green (open) / red (closed).
A persistent, unmissable banner: "REPLAYED DATA — [real event date range]", sourced from data_label in the state contract.
This must never be silently dropped, since it's an explicit acceptance criterion in the PS (never confused with live data).
4.2 Timestep control (the "conditions change" requirement)
A slider or play button stepping through T1→T8. On each step: re-color markers, re-color roads, re-sort the alert sidebar by
priority_rank — all read live from state.json, never hardcoded per-step visuals. This is what proves the platform "updates response
priorities as conditions change," not a static screenshot with a slider bolted on for show.
4.3 Alert sidebar (evidence-ﬁrst, per PS requirement)
Each alert row must display the real evidence block inline — rainfall, elevation, distance to river, nearby-report count — and the
confidence score, not just a risk-level badge. Clicking an alert pans/zooms the map to that settlement.
4.4 Safe-route overlay (bonus)
A toggle that, given a selected affected settlement, draws Member B's computed shortest-path line to the nearest low-risk settlement on
the map, using only currently-open roads.
4.5 Legend & live summary panel
Fixed panel showing: color-key for risk levels and road status, plus a running computed line: "X settlements high-risk · Y roads 
closed · Z ground reports active" — recalculated live from the real current-timestep state, not a static string.
4.6 Test-scenario display
A small panel or PPT slide (whichever is faster) showing the two real test results from Member A/B's validation (Section 2.4): the false-
alert case and the disruption case, with actual numbers, not a claimed-but-unshown "we tested this."

5. Honesty Notes (keep these explicit in the PPT/README — judges reward this)
If real labeled ﬂood-occurrence data wasn't available for training, say so and name the proxy-label rule used instead — this is more
credible than an unstated model.
Don't claim live/real-time capability — the system uses real historical data, replayed and clearly timestamped, which the PS
explicitly permits and rewards when labeled correctly.
Don't claim the model "predicts ﬂoods" in general — frame it as "estimates relative ﬂood risk for this district based on the sourced
historical event," since that's what the data and validation actually support.
6. Acceptance Criteria (must hold true when demoed)
Changing the input rainfall data for a settlement must visibly change its risk_score, risk_level, and its position in the priority
ranking — nothing is hardcoded per settlement.
The false-alert test case must show the model correctly withholding a high-risk label despite high rainfall, when elevation/river-
distance say otherwise.
Advancing the timestep slider must visibly re-color at least one road from open to closed and re-order the alert list — proving the
"conditions change" requirement is real, not decorative.
The safe-route feature must only ever route through roads marked open at the currently selected timestep.
Every alert on screen must carry a non-empty, real evidence block.
